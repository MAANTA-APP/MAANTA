## D162 — what3words quota blocker

**State: OPEN. Blocked solely on founder billing.**

### Provider state

Production what3words returns **HTTP 402 `QuotaExceeded`** — *"Quota exceeded or
API plan does not have access to this feature. Please change your plan at
https://accounts.what3words.com/select-plan"*. The key is present and
well-formed: a missing key returns 503 by a different branch, and what we get is
the provider refusing an authenticated call. This is billing or plan entitlement,
not configuration.

### Re-read of the current implementation (step 1 of the brief)

Confirmed, before changing anything:

- `/api/w3w/validate` is auth-gated (`currentClerkUserId`) and rate-limited, and
  normalises the address before calling out.
- Its dev-only bypass when the key is absent is gated on
  `NODE_ENV === "development"`; production returns 503. It cannot mask a
  production outage.
- Upstream mapping is correct after the earlier fix: a non-2xx is
  `upstream_rejected` → **502** with `serviceDown: true` and the error `code`;
  a 200 with no match stays `not_found` → **200**, still blaming the address.
- The provider's status and error code are logged; **the API key and the address
  are not** (D85 — addresses are PII).
- **No stale fallback path exists.** The onboarding wizard refuses on a non-ok
  response or a falsy `valid`, and "Continue" only enables once an address has
  resolved. Onboarding therefore remains correctly blocked while the provider is
  down — and no bypass was added, per the brief.
- The D162 row is still an accurate description.

### Code changes

None to behaviour. One test file added:
`maanta-app/src/app/api/w3w/validate/__tests__/route.test.ts` — 5 cases:

1. the live 402 shape returns 502 + `serviceDown` + `code`, and never says
   "check the three words";
2. **onboarding stays blocked** — `res.ok` false *and* `valid` false, with no
   `words`/`lat` leaking through, so either half of the wizard gate alone still
   refuses;
3. a genuine no-match still returns 200 and still blames the address;
4. a healthy lookup passes coordinates through;
5. the API key never appears in the response.

Together with the existing `w3w-failure-modes.test.ts` (8 cases) this covers
every property the brief asked for.

### What remains

**Founder billing action is still required.** Nothing further is engineerable.

Post-billing verification, to be run the moment quota is restored:

```

```

then a real merchant walk through `/merchant/onboard` step 2.

**Distinction the brief asked for:**

## D164 — Claims (7d) silently wrong

**State: IMPLEMENTED, tested, committed. NOT deployed, NOT applied to
production — awaiting CI and founder authorization.**

### Root cause

`/admin` and `/founder` both counted claims with
`.gte("created_at", since7d)` on `public.redemptions`. That column has never
existed; the table's only timestamps are `expires_at` (the deal's end plus the
15-minute grace, set at claim but not a claim time) and `redeemed_at` (set at
verification). PostgREST errors, and the two surfaces then failed differently:

- **`/admin`** discarded the error and rendered a confident **0** beside a real
  "Verified (7d) 1" and "Success fees (7d) KES 30".
- **`/founder`** shares one `Promise.all` with every other metric, so the error
  tripped its D149 read-failure guard and **took the whole dashboard down** —
  every visit rendered *"Could not load the dashboard."*

**Escalation worth recording:** the original E2E marked `/founder` as passing
because it returned HTTP 200 with the expected `<h1>`. The dead page returns
exactly that. A shallow assertion hid a completely broken surface, which is the
same failure mode as the unlogged what3words branch: the system reported
success while being broken.

### Migration

`maanta-app/supabase/migrations/20260823140000_redemptions_claimed_at.sql`

Canonical field: **`public.redemptions.claimed_at timestamptz NULL`**, default
`now()`.

Written as two statements deliberately:

```sql
ALTER TABLE public.redemptions ADD COLUMN IF NOT EXISTS claimed_at timestamptz;
ALTER TABLE public.redemptions ALTER COLUMN claimed_at SET DEFAULT now();
```

A single `ADD COLUMN ... DEFAULT now()` would, on Postgres 11+, backfill every
existing row with the migration timestamp — fabricated claim times on a
money-adjacent audit record. Splitting it keeps history NULL and stamps only the
future. An index on `claimed_at` backs the 7-day filter.

### Creation path

**`claim_deal` was deliberately NOT modified.** The column default already
guarantees a database-generated `claimed_at` on every insert path — the RPC,
demo seeding, any future writer — and the value can never be client-supplied.
Re-issuing `claim_deal` would have put its load-bearing body back in play: the
D25 `deal_paused` gate (20260730180000) and the CSPRNG OTP draw (20260818120000).
The cheapest correct change is the one that does not touch it.

No immutability trigger was added: `verify_redemption` never writes
`claimed_at`, and `authenticated` has no write grant on the table (D123). The
guarantee is asserted by test rather than by new machinery on the busiest money
table.

### A third consumer — shopper-facing, found by the parallel trace

`maanta-app/src/app/(shopper)/deals/[id]/page.tsx` ordered its existing-ticket
lookup by the same phantom `created_at`. The query errored, `existingTicketId`
came back null, and `claimable` was computed **true for a shopper who already
held a live pending ticket** — so the page offered "Claim deal" instead of their
ticket, and the tap returned 409.

**This corrects a finding in the earlier E2E report.** That run recorded
"re-claim correctly refused — 409" as a pass. The refusal was real, but it was
the API backstop covering a broken screen; the shopper should never have been
shown the button.

Fixed to `.order("redeemed_at", { ascending: false })` — deliberately *not* the
new `claimed_at`: for a pending row `redeemed_at` IS the claim time and it is
`NOT NULL` on every row, whereas `claimed_at` is NULL for everything claimed
before this migration and Postgres sorts NULLs **first** under `DESC`, which
would surface a stale pre-migration ticket as the newest.

### Metrics

- `/admin` — repointed to `claimed_at`, **and given the honest read-failure
  guard it lacked**, reusing the shared `LeadsReadError` component so both
  dashboards now behave identically on a failed read.
- `/founder` — repointed to `claimed_at`; its existing D149 guard is unchanged.
- Both use the identical definition, asserted by test, so they cannot drift.

### Conversion readiness

No new dashboard was built (out of scope). The schema now makes
`verified / claims` computable for any period: `claimed_at` for the denominator,
`redeemed_at` with `status='success'` for the numerator — from the migration
date forward.

### Historical data — stated plainly

- **How many rows lack `claimed_at` after migration?** Every redemption that
  existed before it — at the production read taken while writing this,
  **401 rows** (396 demo + 5 non-demo). All will be `NULL`.
- **Was anything backfilled?** **No.**
- **Why not?** No stored timestamp defensibly represents the original claim
  event. `expires_at` is derived from the deal's end, not the claim, so it would
  be wrong by up to the deal's whole duration; `redeemed_at` is the verification
  time and exists only for successful redemptions. Inventing either would put
  fabricated data on an audit record.
- **From when is Claims (7d) authoritative?** From the moment
  `20260823140000` is applied to production. The column COMMENT says so, so the
  limitation travels with the schema rather than living only here.

### Tests

- `maanta-app/supabase/tests/redemptions_claimed_at_test.sql` — 6 scenarios:
  column shape (nullable, `now()` default); a real claim is server-stamped
  within the call window; **successful verification does not move it**; **failed
  verification does not move it**; a refused re-claim creates no second row; and
  the KPI's own filter shape finds the claim.
- `maanta-app/src/lib/__tests__/claims-metric.test.ts` — 12 source ratchets:
  both dashboards filter only real columns; neither still uses `created_at`;
  both share one definition; `/admin` inspects errors rather than destructuring
  them away; both render the honest-error component; the migration adds the
  column without a default, keeps it nullable, backfills nothing, indexes it,
  and does not touch `claim_deal`; plus two pinning the shopper ticket lookup.
  **Verified to fail against the old code** — 3/14 on the dashboard regression
  and 2/14 on the shopper one. An earlier draft of the matcher captured nothing
  and made every assertion pass vacuously; that was caught and rewritten, and
  the tests now assert a non-empty capture before checking anything.

### 3 — migration timestamp

Renamed to **`20260823140000_redemptions_claimed_at.sql`**. The original was
dated 24 Aug while the work was done on the 23rd, i.e. future-dated against the
repo's convention of naming by authoring date. `140000` also sits immediately
after the ledger's high-water mark (`20260823130000`), so the intended
application order is explicit. All references updated.

### 4 — what the SQL suite now proves

| Property | Scenario |
|---|---|
| new claims receive `claimed_at` | B — stamped inside the call window, server-side |
| historical rows remain NULL | **G** — a NULL-inserted row stays NULL *and* is excluded from the count |
| verification never changes it | C |
| failed verification never changes it | D |
| the seven-day boundary behaves | **H** — 1 day and 6d23h count, 8 days does not |
| the index exists and is usable | **I** — `idx_redemptions_claimed_at` on `(claimed_at)` |
| tracking start is recorded | **J** — `app_config.claims_tracking_started_at` |
| refused re-claim makes no second row | E |
| the KPI's own filter finds the claim | F |

G asserts the *shape* rather than a row count, because a fresh CI database has
no history while production had 401 rows — a count assertion would pass in one
place and fail in the other for reasons unrelated to the property.

### 7 — the three states, and the KPI label

The migration records `app_config.claims_tracking_started_at` **in the same
transaction that starts tracking**. `src/lib/claims-window.ts` turns it into a
label, shared by both dashboards so they cannot disagree:

| Situation | Label | Caveat line |
|---|---|---|
| config row missing (migration not applied) | `Claims` | "Claim tracking is not enabled yet — this is not a count of zero claims." |
| tracked < 7 days | `Claims since tracking began` | "Claims have only been recorded since 24 Aug — earlier claims are not counted." |
| tracked ≥ 7 days | `Claims (7d)` | none |
| unreadable config value | `Claims` | "…treat this number as incomplete." |
| query failed | *page-level* read-failure state | — |

Deliberately **not** a hover tooltip: these screens are read on a phone at a
counter, where there is no hover, so a caveat only mouse users see is a caveat
most readers never get. It is a quiet line under the number instead. Guarded by
`src/lib/__tests__/claims-window.test.ts` (7 cases, including both sides of the
boundary at 6d23h and exactly 7d).

The date is derived, never hardcoded — so it stays correct regardless of when
the migration is actually applied.

### Challenge — ordering the ticket lookup

Accepted. `redeemed_at` is a fragile recency key: the name implies the
redemption instant, and it only doubles as claim time because it defaults at
insert and is overwritten at verification. The query now orders
**`redeemed_at DESC, id DESC`** so two tickets sharing a timestamp still resolve
deterministically, and the reasoning — including the intent to move to
`claimed_at` with explicit NULL handling once there is enough post-migration
history — is recorded at the call site rather than only here.
